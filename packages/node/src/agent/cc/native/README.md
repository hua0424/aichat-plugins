# CC Windows Job Object helper — build and release

First-party source: `cc-job-supervisor.rs` (Rust standard library + direct Win32 FFI; no external crate). The repository does not declare a license in this directory: the owner must settle distribution terms before external release. Rust standard-library/toolchain components have their own upstream MIT/Apache-2.0 notices; review the toolchain license inventory with the release artifact. No precompiled helper is checked into Git.

**Target:** Windows x64 (`x86_64-pc-windows-msvc`), Node x64, and a native `claude.exe` executable. `CreateProcessW` cannot launch a `.cmd`/`.bat` shim directly. Do not use a shell fallback, because that changes the command trust boundary. Other architectures / missing native binary fail closed during `CcHeadlessDriver.connect()` before receiving a run. POSIX keeps its process-group implementation.

**Build machine (not end user):** Windows x64, Rust `rustc 1.97.1` / 2021 edition, Windows SDK `10.0.26100.0` and VS C++ Build Tools `link.exe`; run `pnpm --filter @aichat/node build` and `pnpm --filter @aichat/node exec vitest run src/agent/cc/windows-job.test.ts`. On a machine with only the Windows SDK, set `CC_JOB_LINKER` to that Rust toolchain's bundled `rust-lld.exe` and `CC_JOB_SDK_LIB` to the SDK's `ucrt/x64;um/x64` import-library directories, then run `node packages/node/scripts/build-cc-job.mjs` from the repository root. These variables change *build linking only*, never runtime paths or job membership. Rebuild after changing source, toolchain or SDK; use a fresh release build directory.

**Artifact:** `packages/node/dist/native/cc-job-supervisor.exe` plus `cc-job-supervisor.provenance.json` (source SHA-256, binary SHA-256, target). The npm `files` manifest includes the executable, provenance, source, and build/verify scripts, even though `dist/` is gitignored. `prepack` rejects missing/mismatched artifacts on Windows and unexpected `dist/native` files; POSIX-only packages remain possible without a helper, but emit an explicit warning and must never be advertised as Windows-capable. A cross-platform package must be packed on Windows x64 or include a previously independently reviewed Windows artifact and matching provenance copied into its release build. On the Windows release builder run `pnpm --filter @aichat/node build`, full tests, `npm pack --dry-run --json` from `packages/node` to check paths, then `npm pack` there and verify the tar contains executable and provenance. The **reviewer** must independently inspect source/Win32 struct ABI, process containment and real child/descendant tests, approve exact source/binary SHA and release toolchain before publishing; a matching self-generated provenance record alone is not an independent approval. Windows end users receive the packed `.exe` and do not need Rust or VS.

**Proof:** `CreateProcessW(CREATE_SUSPENDED)` → assign to job configured `KILL_ON_JOB_CLOSE` → resume; the helper sends child PID only after assignment. Its `D` frame follows queried zero active job processes, a bounded wait for the root process handle to become signalled, verified prompt write (unless cancelled), and drained stdout/stderr. Parent treats missing/partial frames, helper death, missing binary, and unverified stop as unconfirmed; Node `child.close` or `taskkill` alone cannot prove stop. The bounded cancellation in the TS driver waits for explicit proof. `windows-job.test.ts` exercises live detached descendants after root exit, cancel root+descendant, blocked native stdin, malformed control, and parent-control EOF; only own fixture processes are touched.

**Rollback:** restore a previously independently reviewed complete Windows package (Node JS + matching helper + provenance), then restart only the instance explicitly owned by the operator. Do not swap `.exe` alone, use `taskkill` as proof, infer old unknown recovery processes stopped, or deploy from this working tree. Existing recovery records remain `unknown-after-restart` and require separate human verification.
